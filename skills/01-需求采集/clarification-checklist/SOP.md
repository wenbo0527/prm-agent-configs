# clarification-checklist SOP · 需求澄清清单（v1.1）

> **阶段**：01 需求采集
> **目标**：用结构化问题清单澄清模糊需求

---

## 🎯 触发条件

**满足以下任一**：

- ✅ 脑暴后需求仍有歧义
- ✅ 多个方案需要决策
- ✅ 用户对边界 / 优先级不清晰
- ✅ 跨部门协作需要统一理解

## 🛠️ 操作步骤（5 步）

### 第 1 步：列出待澄清问题（5min）

**原则**：不假设，直接列出"我不知道什么"

模板：
```markdown
## 待澄清问题
1. [问题 1] —— 来源：[谁提的]
2. [问题 2] —— 来源：[谁提的]
3. [问题 3] —— 来源：[谁提的]
```

**反范式**：假设用户已经懂 → 直接动手 → 反思≠实证

### 第 2 步：分类问题（5min）

| 类型 | 例子 | 处理 |
|:--|:--|:--|
| **事实类** | "用户数是多少？"|" | 查数据 / 调研 |
| **偏好类** | "要 Web 还是小程序？"|" | 问用户 A/B/C 选项 |
| **边界类** | "要不要做 XX 功能？"|" | PM 拍板 / 升级 |
| **技术类** | "用 Vue 还是 React？"|" | tech lead 决策 |
| **优先级** | "XX 和 YY 哪个先？"|" | 看 ROI / 影响 |

### 第 3 步：选澄清方式（10min）

| 方式 | 适用 | 工具 |
|:--|:--|:--|
| **异步问卷** | 多个用户 / 跨时区 | 飞书 / 腾讯文档 |
| **同步会议** | 内部决策 | 飞书会议 / 腾讯会议 |
| **一对一访谈** | 关键用户 | 1on1 |
| **数据分析** | 已有数据 | SQL / 埋点 |
| **A/B 测试** | 不确定偏好 | 流量分组 |

### 第 4 步：执行澄清（30min-2h）

```
✅ 准备好问题清单
✅ 选对澄清方式
✅ 获得答案后立即记录
✅ 答案有冲突 → 标注 + 升级
```

### 第 5 步：输出澄清结果（10min）

```markdown
## 澄清结果（YYYY-MM-DD）

| 问题 | 答案 | 来源 | 置信度 |
|:--|:--|:--|:--|
| [问题 1] | [答案] | [谁] | 高 / 中 / 低 |
| [问题 2] | [答案] | [谁] | 高 / 中 / 低 |

## 待二次澄清
- [问题 X]（未解决，需升级）
```

## ✅ 验收 Checklist

- [ ] 待澄清问题已分类（事实/偏好/边界/技术/优先级）？
- [ ] 澄清方式与问题类型匹配？
- [ ] 答案有出处（来源 + 置信度）？
- [ ] 输出"澄清结果"文档（建议 1-2 页）？

## 🩸 反范式（4 类常见错误）

### 错误 1：假设代替澄清

- **现象**："我猜用户是 XX" → 直接按假设做
- **后果**：做出来不是用户要的
- **修复**：不假设，必澄清

### 错误 2：问题太大太多

- **现象**：一次性问 20 个问题
- **后果**：用户疲劳，答案质量低
- **修复**：每次问 ≤ 5 个核心问题

### 错误 3：澄清后没记录

- **现象**：口头讨论完就忘
- **后果**：下次又问同样的问题
- **修复**：第 5 步必输出"澄清结果"文档

### 错误 4：答案没追溯

- **现象**："听说是 XX"
- **后果**：答案不可靠
- **修复**：答案必带来源 + 置信度
