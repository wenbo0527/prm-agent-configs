# requirement-understanding SOP · 需求理解（v1.1）

> **阶段**：01 需求采集
> **目标**：把澄清后的需求变成结构化理解

---

## 🎯 触发条件

**满足以下任一**：

- ✅ 澄清清单已完成
- ✅ 需要开始写 PRD
- ✅ 跨团队需要统一理解
- ✅ 复杂需求需要结构化

## 🛠️ 操作步骤（5 步）

### 第 1 步：用户故事（User Story）

模板：
```
作为 [角色]
我想要 [功能]
从而 [业务价值]
```

**示例**：
- ✅ "作为**独立开发者**，我想要**快速记录 TODO**，从而**不遗漏任务**"
- ❌ "用户想要更好的体验"（缺角色 + 业务价值）

**数量**：MVP 通常 5-10 个用户故事

### 第 2 步：验收标准（Acceptance Criteria）

每个用户故事必有 2-5 个验收标准。

模板：
```markdown
### 用户故事 1：[标题]
- [ ] 标准 1（功能正确性）
- [ ] 标准 2（边界 case）
- [ ] 标准 3（异常处理）
```

**反范式**：验收标准 = "能用就行" → 反思≠实证

### 第 3 步：非功能需求（NFR）

| 类别 | 问题 |
|:--|:--|
| **性能** | QPS？响应时间？|
| **安全** | 数据加密？权限控制？|
| **可扩展** | 未来可能加什么？|
| **可维护** | 代码可读性？测试覆盖？|
| **兼容性** | 浏览器？设备？OS？|

**反范式**：只考虑功能不考虑性能 → 上线崩

### 第 4 步：风险评估

| 风险 | 概率 | 影响 | 缓解策略 |
|:--|:--|:--|:--|
| [风险 1] | 高 / 中 / 低 | 高 / 中 / 低 | [策略] |
| [风险 2] | 高 / 中 / 低 | 高 / 中 / 低 | [策略] |

**反范式**：风险评估 = "一切顺利" → 上线爆雷

### 第 5 步：输出需求理解文档

```markdown
# 需求理解 v1.0 · [需求标题]

## 用户故事
1. [用户故事 1]
2. [用户故事 2]
...

## 验收标准
### 用户故事 1
- [ ] 标准 1
- [ ] 标准 2

## 非功能需求
- 性能：[指标]
- 安全：[指标]
- ...

## 风险评估
| 风险 | 概率 | 影响 | 缓解 |
|:--|:--|:--|:--|
| [风险] | [概率] | [影响] | [策略] |
```

## ✅ 验收 Checklist

- [ ] ≥ 5 个用户故事（4 要素：角色/功能/价值）？
- [ ] 每个故事有 2-5 个验收标准？
- [ ] 非功能需求覆盖性能 / 安全 / 可扩展 / 可维护 / 兼容？
- [ ] 风险评估表完整？
- [ ] 文档 ≥ 2 页？

## 🩸 反范式（4 类常见错误）

### 错误 1：用户故事缺要素

- **现象**："用户想要 XX"（没角色）
- **后果**：不知道为谁做
- **修复**：4 要素必齐全

### 错误 2：验收标准模糊

- **现象**："系统应该快"
- **后果**：争议
- **修复**：量化（响应时间 < 200ms）

### 错误 3：NFR 缺失

- **现象**：只写功能，没写性能 / 安全
- **后果**：上线崩
- **修复**：5 类 NFR 必覆盖

### 错误 4：风险评估走过场

- **现象**：风险 = "无"
- **后果**：没准备应急方案
- **修复**：至少列 3 个真实风险 + 缓解策略
