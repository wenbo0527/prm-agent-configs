# documentation-and-adrs SOP · 文档与 ADR（v1.1）

> **阶段**：09 文档沉淀
> **目标**：把决策和知识沉淀为可复用文档

---

## 🎯 触发条件

- ✅ 重大技术决策
- ✅ 项目闭环
- ✅ 知识需要传递

## 🛠️ 操作步骤（5 步）

### 第 1 步：识别"需要文档化"的内容

| 内容 | 文档类型 |
|:--|:--|
| 技术选型理由 | ADR (Architecture Decision Record) |
| 项目闭环 | Postmortem / Retrospective |
| 用户故事 | PRD / User Story |
| API 接口 | OpenAPI / Swagger |
| 架构 | 架构图 / 系统设计 |
| 流程 | SOP / Runbook |
| 教训 | Lessons Learned |

### 第 2 步：ADR 模板

```markdown
# ADR-[编号] · [决策标题]

## 状态
[Proposed / Accepted / Deprecated]

## 背景
[什么问题 / 什么场景]

## 决策
[我们决定怎么做]

## 理由
[为什么这样做]

## 后果
[优点 / 缺点 / 风险]

## 替代方案
[考虑了哪些 / 为什么没选]
```

### 第 3 步：文档分层

```
文档金字塔：
- README（5min 懂项目）
- ARCHITECTURE（30min 懂架构）
- ADR（理解关键决策）
- API doc（开发参考）
- Runbook（运维参考）
```

### 第 4 步：文档评审

```
评审清单：
- [ ] 5min 能否看懂？
- [ ] 关键决策有记录？
- [ ] 链接齐全（前后引用）？
- [ ] 图表清晰？
- [ ] 更新日期？
```

### 第 5 步：维护 + 归档

```
维护：
- 代码变更 → 同步更新文档
- 架构变更 → 写 ADR
- 季度 review → 更新 README

归档：
- docs/
- wiki/
- ADR/（按时间排序）
```

## ✅ 验收 Checklist

- [ ] 必含文档类型 ≥ 3？
- [ ] ADR 6 字段齐全？
- [ ] 文档金字塔 5 层覆盖？
- [ ] 评审清单 5 项？
- [ ] 归档 + 维护机制？

## 🩸 反范式

- **决策没文档** → 后来人不知道为啥这样
- **文档过期** → 误导
- **文档孤岛**（无链接）→ 用不起来
