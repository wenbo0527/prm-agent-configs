# requirement-breakdown SOP · 需求拆解（v1.1）

> **阶段**：03 需求拆解
> **目标**：把 PRD 拆成可执行子任务

---

## 🎯 触发条件

- ✅ PRD 已锁定 v1.0
- ✅ 即将进入开发执行
- ✅ 需要给 dev lead / 各角色派单

## 🛠️ 操作步骤（5 步）

### 第 1 步：识别"完成定义"（DoD）

每个子任务必带 DoD：

```markdown
### 子任务 ST1.1
**标题**：[明确动作]
**责任角色**：[dev lead / dev1 / QA]
**DoD**：
- [ ] 代码完成（含单元测试）
- [ ] PR merged 到 main
- [ ] QA 测试通过
- [ ] 文档更新
```

### 第 2 步：拆到最小可执行

```
拆分原则：
- 1 个子任务 = 1 个人 + 1-3 天
- 不要跨周（除非是基础设施）
- 必有清晰交付物（代码 / 文档 / 测试）

反范式：
- 1 个任务 2 周 → 拆 5 个
- 1 个任务 3 人 → 拆 3 个
```

### 第 3 步：识别依赖关系

```
依赖图：
ST1.1 → ST1.2 → ST1.3（顺序）
ST2.1 ⟂ ST2.2（并行）
ST3.1 ← ST1.2（依赖）

可视化：Mermaid / Graphviz / 表格
```

### 第 4 步：估算工作量

| 方法 | 适用 |
|:--|:--|
| **T-shirt size** (S/M/L) | 粗估 |
| **人天** | 中等精度 |
| **故事点** | Scrum 团队 |
| **绝对工期** | 关键路径 |

**反范式**：估算 = 拍脑袋 → 风险

### 第 5 步：输出 WBS

```markdown
# WBS · [项目名] v1.0

## 总览
- 总任务：15 个
- 总工期：4 周
- 关键路径：ST1 → ST2 → ST5 → ST10

## 子任务清单

### 模块 1：[模块名]
| ID | 标题 | 角色 | 工时 | DoD | 依赖 |
|:--|:--|:--|:--|:--|:--|
| ST1.1 | [动作] | dev | 2d | [DoD] | - |
| ST1.2 | [动作] | dev | 1d | [DoD] | ST1.1 |

### 模块 2：[模块名]
...
```

## ✅ 验收 Checklist

- [ ] 每个子任务有 DoD？
- [ ] 1 子任务 = 1-3 天？
- [ ] 依赖图清晰？
- [ ] 工作量估算有方法？
- [ ] WBS 文档 ≥ 2 页？

## 🩸 反范式

- **拆太粗**：1 子任务 2 周 → 反思≠实证
- **拆太细**：1 子任务 1 小时 → 派单成本 > 工作量
- **不识别依赖**：并行任务互相阻塞 → 浪费
