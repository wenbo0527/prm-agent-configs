# 团队 3 · 1 人 PM 阵型（v1.0）

> **适用**：个人项目 / 独立开发者
> **规模**：1 个 agent（PM 兼所有）
> **场景**：个人产品 / 副业 / 学习项目

---

## 🏛️ 阵型结构

```
                  ┌──────────────┐
                  │     PM       │
                  │ 派工+跟踪+验收│
                  │ + 产品       │
                  │ + dev        │
                  │ + QA         │
                  │ + doc        │
                  └──────────────┘
```

## 👥 角色职责（PM 兼所有）

### PM（兼产品 + dev + QA + doc）

| 职责 | 不做 |
|:--|:--|
| 派工给自己 | 派工给别人（无别人） |
| PRD 撰写 | — |
| 需求拆解 | — |
| 代码开发 | — |
| 自测试 | — |
| 文档沉淀 | — |

## 🔄 工作流（极简）

```
PM 接收需求（自己想的）
   │
   ▼
PM：脑暴 + 澄清 + 需求理解
   │
   ▼
PM：写 PRD（可选）
   │
   ▼
PM：拆 WBS（即使一个人也拆）
   │
   ▼
PM：派工给自己（task_tool create）
   │
   ▼
PM：开发
   │
   ▼
PM：自测试（cross-check ≥ 2 维度）
   │
   ▼
PM：闭环 + 教训
```

## 📋 派工路径

```
PM → 自己
```

**为什么还派工？** 即使一个人，也要走 task_tool create → update → close 流程，确保：
- 任务可视化（task board 有记录）
- 反思≠实证（update 后必 get）
- 闭环可追溯

## 🚨 "升级"路径

```
冲突？ → 自己决策
阻塞？ → 自己突破
```

但在以下情况，建议找外部 review：
- 架构决策 → CTO/技术 mentor
- 战略决策 → 朋友/合伙人
- 反思≠实证严重违例 → 写教训公开

## 📊 协作健康度指标

| 指标 | 目标 |
|:--|:--|
| 派工（给自己）5 件套完整率 | 100% |
| 任务可视化率 | 100% |
| 反思≠实证次数 | = 0 |
| 任务 24h 推进率 | > 50%（人手有限） |
| 闭环文档化率 | > 80% |

## ⚖️ 与多人阵型的差异

| 维度 | 5 人 | 3 人 | 1 人 |
|:--|:--|:--|:--|
| 派工对象 | 子角色 lead | 子角色 lead | 自己 |
| 升级路径 | PM → CTO | PM → CTO | 自己 → mentor |
| 一次验收通过率 | > 80% | > 70% | > 60% |
| 反思≠实证 | = 0 | = 0 | = 0 |
| 任务可视化 | 100% | 100% | 100% |

## 💡 1 人阵型的关键

即使只有一个人：
- **必走派工 SOP**（给自己也派）
- **必走 task_tool create/update/get**
- **必走验收 Checklist**
- **必写教训**

**为什么？** 因为这是建立"工程纪律"的过程。1 人养成习惯，5 人时无缝切换。
