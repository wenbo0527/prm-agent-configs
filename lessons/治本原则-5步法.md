# 治本原则 5 步法 · 范式（v1.0）

> **核心问题**：bug / 任务反复出现，只改表象不除根
> **锁版守**：复杂问题必走 5 步法（现象→假设→根因→修复→预防）

---

## 🎯 范式定义

**治本** = 找到根本原因并修复，避免问题反复
**治标** = 只改表象，问题下次还会出现

5 步法 = 找到根本原因的系统方法

## 🛠️ 5 步法

### 第 1 步：现象（准确记录"看到了什么"）

**不评判，只描述事实**

```
✅ "任务 TASK-X 派给 dev，24h 后状态仍 in_progress"
✅ "用户登录后页面空白"
✅ "每天 9 点 cron 失败"
```

**反例**：
```
❌ "dev 没干活"（评判）
❌ "代码有 bug"（太模糊）
```

### 第 2 步：假设（列出 ≥ 3 个可能根因）

**至少列 3 个，从不同维度：技术 / 流程 / 团队 / 边界 / 范式**

```
✅ 技术：dev 任务太复杂 / 接口文档不全
✅ 流程：派单缺验收标准 / 跟踪机制弱
✅ 团队：dev 忙于其他任务 / dev 不熟业务
✅ 边界：派单越级导致 lead 失权
✅ 范式：反思≠实证导致假完成
```

### 第 3 步：根因（用工具实证定位）

**不靠猜，靠实证**

```
✅ grep -rn "TASK-X" /path/  → 找到任务出现位置
✅ cat /path/to/file  → 看实际内容
✅ stat /path/to/file  → 看 mtime
✅ task_tool.py get TASK-X  → 看任务真实状态
✅ cross-check ≥ 2 workspace  → 跨空间验证
```

**实证后**才能定位根因。例如：
```
实证发现：dev 没收到通知（grep 不到 TASK-X 在通知系统）
实证发现：派单 update 失败（task_tool get 显示 status=pending）
```

### 第 4 步：修复（改根因而非改表象）

**改根因 = 一次性根治**

```
✅ 根因"派单缺验收标准" → 修复：派工 SOP 加必填验收项
✅ 根因"派单 update 失败" → 修复：加二次实证 SOP
✅ 根因"dev 没收到通知" → 修复：通知系统加固
```

**反例**（治标）：
```
❌ 看到任务卡 → 手动推进（下次还会卡）
❌ 看到 bug → 注释掉代码（下次还会出现）
❌ 看到超时 → 加超时时间（治标不治本）
```

### 第 5 步：预防（写教训）

**位置 + 风险 + 修复 + 验证** 四件套

```markdown
## 教训

**位置**：[文件路径:行号 / TASK-ID]
**风险**：[可能引发什么问题]
**修复**：[具体修复动作]
**验证**：[怎么证明修复了]
```

## 🩸 反范式（5 类常见治标）

### 反范式 1：直接动手不分析
- **现象**：看 bug 直接修，不找根因
- **后果**：下次还会出
- **修复**：5 步法第 1-3 步必走

### 反范式 2：治标不治本
- **现象**：加超时 / 注释代码 / 手动重试
- **后果**：问题反复
- **修复**：第 4 步必改根因

### 反范式 3：不写教训
- **现象**：修了但没写教训
- **后果**：下次别人踩同一个坑
- **修复**：第 5 步必写四件套

### 反范式 4：单维度假设
- **现象**：只看技术维度，不看流程/团队
- **后果**：根因定位不准
- **修复**：第 2 步至少 3 个维度

### 反范式 5：反射≠实证
- **现象**：觉得"应该是 X"，不实证
- **后果**：修复错方向
- **修复**：第 3 步必实证

## 📋 5 步法 Checklist

- [ ] 第 1 步：现象描述无评判？
- [ ] 第 2 步：假设 ≥ 3 个维度？
- [ ] 第 3 步：用工具实证（grep/cat/stat）？
- [ ] 第 4 步：改的是根因不是表象？
- [ ] 第 5 步：写教训带四件套？

---

*锁版守：5 步法不可跳步 + 改根因而非治标 + 写教训带四件套*
